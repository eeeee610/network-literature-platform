### 1.1 启动方式

当前后端是一个 Spring Boot 应用，A/B/C/D 是同一应用内的业务模块，并非四个可分别部署、分别监听端口的服务。因此“模块独立启动”按以下口径检查：

1. 整个 Spring Boot 应用能否加载四个模块并启动。
2. 各模块路由是否注册，鉴权和控制器是否生效。

- **通过**：本次实际执行并得到预期结果。

- **阻塞**：因 MySQL、测试账号或运行环境缺失，不能给出业务通过结论。

## 4. 认证、权限、异常、事务与重复操作评审

### 4.1 认证与权限

已确认的有效控制：

- 公共拦截器保护 A 账户和 D 后台路由。
- D 后台要求 `ADMIN`，读者令牌实测返回 403。
- B 作者服务包含作品归属检查。
- D 防止管理员锁定或禁用当前自身账号。

已确认的问题：

1. 公共白名单包含 C 的公共 GET，却遗漏 B 的公共 GET。
2. B 在公共认证之外再次解析 JWT；A/公共使用 `JwtProperties`，B 使用独立 `JwtTokenParser`，默认密钥分别为不同值，环境配置入口也不一致。
3. 公共拦截器验证签名、有效期和角色后，不重新检查用户当前状态；D 的锁定/禁用对既有令牌的即时约束力不足。
4. VIP 阅读只有收费记录，没有跨 A/B 的阅读授权闭环。

### 4.2 异常处理

- 注册空参数、未登录和越权分别返回统一 400、401、403 结构。
- 数据库不可用时仍观察到统一 500 响应，没有泄露为前端自定义 mock 成功结果。
- 真实业务唯一键冲突、存储过程异常及并发冲突的 API 错误映射，仍需在 MySQL 可用后验证。

### 4.3 事务一致性

- A 订阅、打赏存储过程自行管理事务，服务层未再叠加可能冲突的 `@Transactional`；退款使用应用事务。
- C 评论、评分和榜单相关写流程按调用方事务边界组织。
- D 内容审核将状态更新与审核日志放在同一事务。
- 历史 47 项跨模块 SQL 测试已验证多种提交和回滚场景，但不能替代当前应用层事务传播、连接和异常映射验证。

### 4.4 重复操作与并发

- A 服务测试覆盖重复订阅、重复打赏及退款行为。
- C 点赞有防重处理，重复评论审核依赖状态及计数机制。
- B 重复发布、A 重复订阅/打赏、C 重复点赞及榜单同期次重建有历史 SQL 证据。
- 多线程同时订阅、同时打赏、同时评分、并发审核和前端重试未在本次真实环境执行，不能标记为通过。

### 7.2 主要风险
